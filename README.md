# 差旅数据整合与分类工具

一个面向财务月报场景的多源差旅数据整合工具，用于将携程、滴滴、Payment、OA 等结构不同的数据文件统一完成读取、字段标准化、申请单 Mapping、固定分类、质量检查和宽表输出。

> **这个工具的核心价值，是将多个结构不同的差旅数据源自动整理成统一、可用于月报分析的标准宽表。**

项目以 Python 确定性处理为核心。无法通过固定规则可靠分类的记录不会被强行判断，而是进入人工确认清单。当前公开版本不调用 LLM，也不将项目包装为 AI 审批产品。

## 1. 项目简介

财务人员在编制差旅月报时，通常需要从多个平台获取明细。不同系统的字段名称、日期格式、订单编号、部门结构和费用分类口径并不一致，直接合并很难用于后续分析。

本项目提供一个简洁的 Streamlit 工作台，让使用者能够：

- 选择内置模拟数据，或上传自有测试文件。
- 查看系统识别出的数据来源和原始记录数。
- 一键完成标准化、Mapping、分类、合并和质量检查。
- 快速定位 Mapping 缺失、字段异常和待人工确认记录。
- 下载标准化月报底表及待人工确认清单。

## 2. 业务背景

多源差旅数据整合常见以下问题：

- 各平台导出文件的字段结构和命名不一致。
- 差旅申请单号与订单号、报销单据号之间需要额外关联。
- 场景和类型口径分散，难以直接汇总到统一月报。
- 住宿晚数等分析字段需要二次计算。
- 固定规则无法覆盖所有业务描述，仍需保留人工判断。
- 数据质量问题如果未被显式标记，容易在月报阶段被忽略。

本项目将上述步骤整理为可重复运行的数据处理流程，同时保留每条记录的原始描述，方便财务人员追溯。

## 3. 支持的数据源

当前版本支持 5 类模拟数据源：

| 数据来源 | 主要处理内容 |
| --- | --- |
| 携程 | 机票、酒店及其他项目类别标准化，提取关联行程号并计算住宿晚数 |
| 滴滴用车 | 用车字段标准化，根据事由、备注和时间信息进行固定规则分类 |
| 滴滴火车 | 火车订单标准化，并通过订单号关联差旅申请单 |
| Payment | 解析摘要中的申请人、单据号和部门，并按费用类型完成固定 Mapping |
| OA 报销 | 解析报销单据号，完成费用类型 Mapping 和住宿晚数计算 |

系统通过 Excel 字段结构识别数据源，不要求用户提前修改文件名。

配套文件：

- `travel_mapping.xlsx`：差旅申请单号与费用订单号 / 申请单据号的模拟关联表。
- `travel_master_template.xlsx`：最终标准宽表的字段模板。

## 4. 数据处理流程

```text
选择 Mapping 与差旅数据源
          ↓
识别数据源及原始记录数
          ↓
数据读取与字段标准化
          ↓
差旅申请单 Mapping
          ↓
场景 / 类型固定分类
          ↓
多源数据合并
          ↓
数据质量检查
          ↓
标准月报宽表 + 待人工确认清单
```

Streamlit 页面按照以下业务顺序展示：

`输入了什么 → 处理了多少 → 出现什么问题 → 最终输出是什么`

## 5. 核心处理逻辑

当前已实现并保留的核心逻辑包括：

- 携程数据读取与字段标准化。
- 滴滴用车数据读取与固定规则分类。
- 滴滴火车数据读取与字段标准化。
- Payment 数据摘要解析与费用类型 Mapping。
- OA 报销数据读取、Mapping 与住宿晚数计算。
- 差旅申请单号、订单号和申请单据号关联。
- 境内外、场景和类型的固定映射。
- 多源标准数据合并。
- 待人工确认记录识别。
- 标准化 Excel 宽表导出。

## 6. 数据标准化规则

不同数据源最终统一到以下标准字段：

- 数据来源
- 差旅申请单号
- 申请单据号 / 订单号
- 申请人及员工邮箱
- 一级部门及二级部门
- 费用日期与城市
- 境内外、场景和类型
- 币种与金额
- 住宿晚数
- 是否敏感
- 原始描述
- 分类方式
- 是否需要人工确认

页面日期统一显示为 `YYYY-MM-DD`。金额保留为数值并按两位小数展示，下载文件中的日期和金额也设置了对应的 Excel 格式。

## 7. Mapping 与分类逻辑

### 差旅申请单 Mapping

`travel_mapping.xlsx` 使用“费用订单号 / 申请单据号”关联“差旅申请单号”。系统不会因 Mapping 缺失而删除记录，而是在质量检查区域进行标记。

### 分类方式

前端统一显示三种分类方式：

- `固定规则`：根据确定性文本条件或时间规则完成分类。
- `固定 Mapping`：根据已有费用类型或项目类别直接映射。
- `待人工确认`：现有规则无法可靠确定场景或类型。

后台仍保留 V1 原有分类结果和业务取值，前端仅对技术名称进行更易理解的中文展示。

## 8. 数据质量检查

系统在合并完成后执行非破坏性质量检查，当前包括：

- 差旅申请单号缺失
- Mapping 未匹配
- 关键字段缺失
- 金额为空、非数字或小于等于 0
- 完全重复记录
- 无法通过固定规则完成分类

质量检查只负责发现和展示问题，不会自动删除、覆盖或修改原始记录。

## 9. 人工确认机制

只有无法通过固定规则或固定 Mapping 可靠分类的记录才会进入“待人工确认”区域。

每条记录会直接展示：

- 数据来源、申请人和费用日期
- 原始描述
- 当前场景和类型
- 未能自动分类的原因
- 建议处理方式

对于固定规则无法可靠分类的记录，当前版本保留人工确认。后续可按需增加语义辅助分类能力，但最终判断仍应由财务人员完成。

## 10. 最终输出

页面提供两个下载文件：

| 文件 | 内容 |
| --- | --- |
| `travel_monthly_master.xlsx` | 全部成功整合的标准化差旅月报底表 |
| `travel_review_items.xlsx` | 仅包含需要人工确认的记录 |

内置模拟数据当前处理基线：

| 指标 | 结果 |
| --- | ---: |
| 数据源数量 | 5 |
| 原始记录数 | 23 |
| 成功整合记录数 | 23 |
| 固定规则 / Mapping 完成分类数 | 19 |
| 待人工确认数 | 4 |

这些数字由当前模拟数据动态计算，不是写死在页面中的展示值。

## 12. 本地运行方式

建议使用 Python 3.10 或以上版本，并安装 Streamlit 1.50 或以上版本。

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
python3 -m streamlit run app.py
```

页面打开后，默认选择“使用内置模拟数据”。点击“开始数据整合”即可完整运行 5 个数据源的处理流程。

## 13. 模拟数据与隐私说明

- 所有 Excel 文件均为模拟数据。
- 员工姓名、邮箱、部门、订单和申请单编号均为虚构内容。
- 项目不包含真实公司内部 Mapping、真实费用数据或内部制度。
- 项目不需要 API Key、Token 或 Password。
- 原始上传文件不会被修改。

## 14. 当前限制

- 当前仅支持项目中已定义的 5 类 Excel 数据结构。
- 数据源识别依赖必要字段组合，字段结构发生较大变化时需要更新解析器。
- Mapping 覆盖率取决于上传的差旅申请关联表完整性。
- 固定分类规则无法覆盖所有自由文本业务描述。
- 当前未提供页面内人工回填和重新计算功能。
- 当前未实现数据库写入、权限管理、操作日志和定时任务。
- 项目定位为月报数据准备工具，不是生产级差旅管理系统。
